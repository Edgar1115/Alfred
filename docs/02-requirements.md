# 需求与能力规划

## 1. 能力域总览

Alfred 的能力按域拆分，组成"无论如何都能帮上忙"的全方位管家：

```
                      ┌─────────────────────────────┐
                      │      输入层 (语音 + 文本)      │
                      │  语音转写 · 唤醒 · 意图预读    │
                      └──────────────┬──────────────┘
                                     ▼
              ┌──────────────────────────────────────┐
              │          核心理解与调度层             │
              │  (意图识别 · 槽位抽取 · 技能路由)      │
              └──────────────────────────────────────┘
     ┌──────────────┬──────────────┬─────────────┬──────────────┐
     ▼              ▼              ▼             ▼              ▼
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   ┌──────────┐
│ 日程与提醒 │  │ 长期记忆  │  │财务与健康 │  │ 生活辅助  │   │ 情绪陪伴  │
└──────────┘  └──────────┘  └──────────┘  └──────────┘   └──────────┘
```

## 2. 能力域详解与需求分级

需求分级约定：
- **P0**：MVP 必须具备，完成最小可用闭环
- **P1**：核心体验的合理补充
- **P2**：进阶/锦上添花

### 1.1 交互设计原则：对话优先（Conversation-First）

**Alfred 的产品形态是"助手本身"，不是功能集合。** 用户打开 Alfred 面对的是对话，日常一切操作——增、查、改、汇总——通过跟 Alfred 说话/打字完成。管理界面（日程列表、记账本、记忆档案）**存在但刻意弱化**：

- 管理界面是"后台"：用于人工校对、纠错、审计，不承载日常高频使用
- 默认引导：任何查询动作优先应答对话（`我下周有什么安排？` → 直接回答，而非跳转列表）
- 界面层级上对话是唯一一等公民，功能页是二级入口
- 用户只需要记住一句话——**"有事跟 Alfred 说"**

### 2.0 语音输入与常驻聆听（P0）

管家以「说话」为第一等交互，且**从应用启动就持续聆听**——不是"被唤醒"，而是"一直在"。Alfred 听的同时持续判断每句话的价值，决定如何对待。

| ID | 需求 | 优先级 | 说明 |
|----|------|--------|------|
| VOI-01 | 语音 → 文本转写（本地/云端可切换） | P0 | 支持中英文，命令式口吻即可 |
| VOI-02 | 连续说：自然语言理解接转写结果 | P0 | "明早 7 点叫醒+带护照" 整句语义 |
| VOI-03 | 常驻聆听 | P0 | 应用启动即持续聆听（默认）；按键/唤醒词为辅助 |
| VOI-04 | 语音输出（可选 TTS） | P1 | 管家回复可朗读（可选，防止轰炸） |
| VOI-05 | 多语言 | P2 | 中/英/粤等 |
| VOI-06 | 环境降噪 | P2 | 降噪/回声消除，做菜/走路也能听得清 |
| VOI-07 | 语音安全网 | P0 | 对指令中的危险语义（自伤等）转文本后走心理安全线路由 |

> ⚠️ **常驻聆听的隐私边界**：默认常驻聆听，但**透明可控**——常驻「聆听中」指示；一键闭麦；录音仅在本地处理、识别后即丢弃（不上传原始音频）；用户可彻底关闭常驻聆听，退回按键/唤醒触发。

### 2.7 多端与同步（P0）

Alfred 是**三端一管家**：电脑 / 手机 / 平板各自是完整应用，不依赖某台"主设备"，数据通过云端账号自动同步。

| ID | 需求 | 优先级 | 说明 |
|----|------|--------|------|
| MULTI-01 | 三端客户端 | P0 | 桌面（macOS/Windows/Linux）、手机（iOS/Android）、平板自适应；一套代码基座 |
| MULTI-02 | 账号系统 | P0 | 同一账号登录所有端；未登录也可作为本地单机用 |
| MULTI-03 | 数据自动同步 | P0 | 任意端改动，登录同账号的其他端自动同步；冲突可解决 |
| MULTI-04 | 离线可用 | P0 | 断网时数据库本地照常增删查 + 提醒照常触发，联网后合冲 |
| MULTI-05 | 自适应 UI | P0 | 出厂前各屏幕（含异形屏/刘海/折叠）都适配；横竖屏自动切换 |
| MULTI-06 | 本地推送 | P1 | 本端提醒使用系统通知（手机/桌面/平板） |
| MULTI-07 | 端对端加密 | P2 | 敏感数据端到端加密（优先级低于正确性） |
| MULTI-08 | 多端记忆一致性 | P1 | 记忆、档案等语义数据同步一致 |
| MULTI-09 | 对话主界面 | P0 | 三端统一以对话为主界面；管理页（日程/记账/档案）为二级后台入口，不做主导航 |

### 2.7.1 双版本分发（P0，横切）

Alfred 面向**两大人群**：懂技术、想自部署的开发者（Community / 自托管），以及想要傻瓜式体验的大众用户（Cloud / 官方）。二者基于**同一套代码**构建，能力对齐，仅**基础设施由谁提供**不同：

| ID | 需求 | 优先级 | 说明 |
|----|------|--------|------|
| RELEASE-01 | 双发行形态 | P0 | 同一 Flutter 客户端 + `core/` 业务核心，通过 Build Flavor/Provision 产出：`community`（自托管）与 `cloud`（官方）两种包 |
| RELEASE-02 | 基础设施可配置 | P0 | LLM / ASR / 同步 relay / 账号全部通过 Provider 注入：自托管版可配自带 Key / 本地模型 / 自建 relay；Cloud 版默认指向官方服务 |
| RELEASE-03 | 自托管一键部署 | P1 | 提供 Docker 一键部署（relay + 可选 ASR/LLM 网关），配合安装文档，低门槛自部署 |
| RELEASE-04 | 能力对齐不分裂 | P0 | 双版本共享 core/ 能力（日程/记忆/语音/价值分层/同步）；**不自建"社区 Pro"阉割版**；商业模式只作用于托管服务本身 |
| RELEASE-05 | 开源协议 | P2 | 许可证**待定**（倾向 AGPL-3.0）；选定后明示源码托管、构建方式、自托管指南 |

> 设计含义：**社区版不是"残缺版"**，而是"你自己提供服务的 Cloud 版"。任何人可在不依赖官方的情况下获得全量 Alfred。

### 2.8 对话优先（P0，横切原则）

对话优先不是"某一块技能"，而是贯穿所有能力域的**界面与交互原则**：

| ID | 需求 | 优先级 | 说明 |
|----|------|--------|------|
| DLG-01 | 对话为唯一一等界面 | P0 | 启动即对话；语音/文本输入始终可达 |
| DLG-02 | 查询默认对话应答 | P0 | "我下周有什么安排" → 直接在对话里报结果，不跳列表页 |
| DLG-03 | 管理页弱化入口 | P0 | 日程/记账/档案管理页只在二级导航（如设置→数据管理），不设主 Tab |
| DLG-04 | 对话内确认 | P0 | 创建/修改/删除在对话中完成（含可撤销），无需跳表单页 |
| DLG-05 | 对话内汇报 | P1 | 报表（月度支出汇总等）默认以对话卡片呈现，图表可为辅助 |

> 设计原则：**用户不需要学会"界面"，只需要学会"跟 Alfred 说话"。**

### 2.9 价值分层判断（P0，横切原则）

Alfred 持续聆听，但**不是每句话都要行动**。它要在极低误判率下把听到的内容分三层：

| 层 | 定义 | Alfred 的做法 | 示例 |
|----|------|--------------|------|
| **真事（委托）** | 包含明确"让 Alfred 办"的意图：日程、待办、记账、提醒、委托 | **轻声确认后执行**；确认前不落库 | "明晚 7 点健身" "记一笔买菜 128" |
| **该记的（吸收）** | 用户没要求记、但值得存档：偏好、家事、关系、情绪信号 | **静默写入记忆**，不打断当前活动 | "我喜欢喝美式" "奶奶喜欢龙井" "最近好累" |
| **废话（忽略）** | 闲聊、自言自语、追问、环境声、无意义内容 | 不打扰、不记录、不触发任何行动 | 路上闲聊、跟旁边人说"你吃了吗" |

对应需求：

| ID | 需求 | 优先级 | 说明 |
|----|------|--------|------|
| VAL-01 | 价值分层分类器 | P0 | 基于 LLM+规则；将每个语音片段分层为 委托/吸收/忽略 |
| VAL-02 | 委托类先确认 | P0 | 识别为委托 → 轻声复述确认（"要记'明晚 7 点健身'吗？"）→ 用户确认才执行 |
| VAL-03 | 吸收类静默写入 | P0 | 识别为偏好/家事/情绪 → 静默入记忆，不打断（满足"用户没说记就记下"） |
| VAL-04 | 忽略类零打扰 | P0 | 不说、不做、不记录，绝不打断 |
| VAL-05 | 误判兜底 | P0 | 确认可撤销；记忆吸收可随时在管理页删除/修正 |
| VAL-06 | 话轮边界 | P1 | 识别"这句话是对 Alfred 说的 vs 对旁边人说的"，避免误动作 |

> **判断力是 Alfred 的核心卖点**：不是能听懂，而是**知道哪些话值得它弯腰**。

## 3. 用户故事（示例）

> **作为** 一个忙碌的上班族
> **我想要** 明早 7 点收到航班提醒
> **所以** 我不会误机

> **作为** 一个经常在电脑手机间切换的人
> **我想要** 手机上确认的事项，电脑上立刻能看到
> **所以** 我不需要重复登记，也没信息孤岛

> **作为** 一个通勤族
> **我想要** 地铁里（断网）能正常记录和查看
> **所以** 管家离线也靠得住

> **作为** 一个双手经常占着的人
> **我想要** 随口说一句就能让管家记下
> **所以** 我不需要被打断，生活更顺

> **作为** 一个关注健康的人
> **我想要** 记得每天吃维生素
> **所以** 我不用靠脑力记住

> **作为** 一个压力大的人
> **我想要** 有地方倾诉，Alfred 不打断我的感受
> **所以** 我感受被听见，而不是被解决

> **作为** 一个不想学界面的人
> **我想要** 查一切问 Alfred 就行，不用翻各种列表页
> **所以** 我打开 Alfred 永远是同一个动作——对管家说话

> **作为** 一个生活节奏快、不爱敲字的人
> **我想要** 走到哪说到哪，有些事主动说给它，有些事它自己听着记着
> **所以** 我不需要专门"打开提醒"或"记一笔"，日子照过，Alfred 自己分类处理

> **作为** 一个在乎分寸的人
> **我想要** 说"明晚 7 点健身"它会确认，说"奶奶喜欢龙井"它默默记下，身边别人说话它不应声
> **所以** 我相信它知道什么时候该出手、什么时候该闭嘴

## 4. 非功能需求

| 类型 | 要求 |
|------|------|
| 可靠性 | 提醒漏发率 = 0；所有破坏性操作可撤销 |
| 隐私 | 数据本地存储优先（本地 SQLite），可一键导出 / 清空；常驻聆听透明可控（聆听指示、一键闭麦、本地转写即丢弃、可完全关闭） |
| 性能 | 意图解析 < 800ms（单条命令）；语音转写 < 1s（单人短句）；常驻聆听功耗与响应符合移动端标准 |
| 可用性 | 断网仍可用基础能力（含本地语音转写降级）；多端离线照常 |
| 一致性 | 多设备同步最终一致；冲突率 < 0.1%；单设备操作始终可用 |
| 可扩展 | 新技能以插件式挂载，不改核心 |
| 判断质量 | 真事（委托）召回率 >95%；废话误判率 <2%（不该打断却打断） |
